1: # Combat Plan 1.2：事实、表达与复核
2: 
3: 权威结构：[当前 Schema](../assets/combat-plan.schema.json)。[1.0 Schema](../assets/combat-plan-v1.schema.json) 只供迁移与结构检查。软件版本和数据契约版本分别维护；文本创作不强制填写 JSON。

5: 当前兼容读取 1.1，1.2 增加可选动作结构与素材证据。旧案例不被强制补写未知动作事实；1.0 必须显式迁移并重新复核。已标 available/bound 的旧素材声明需补证据，不能仅迁移版本号后当作已验证。
6: 
7: ## 字段职责与交接
8: 
9: | 字段 | 权威角色 | 交付位置 |
10: | --- | --- | --- |
11: | duration / aspect_ratio / generation / camera_mode / timing / rules | 时间、镜头和能力的硬约束 | prompt 硬约束、设计卡、交接单 |
12: | cast / abilities / anchors / initial_state | 人物、持物、能力和开场事实 | prompt 硬约束、导演稿、编译交接 |
13: | beats | 动作、表演、机位、声音与状态事实 | director.md、prompt-handoff.json |
14: | weapon_profiles / action_initial_state / action_events / state_delta | 可选具体交手；启用时为动作状态的唯一权威 | prompt 具体交手、投影状态、编译交接；见[动作契约](action-contract.md) |
15: | sections.beat_ids | 投喂段选取的连续细拍 | 导出时间范围与交接记录 |
16: | headers / sections.summary | 人工或 Agent 编写的表达 | prompt.txt；需要语义复核 |
17: | editorial_reviews | 对特定输入和表达版本的复核声明 | 计划与状态检查；不是视频验收 |
18: | id / provenance | 文件身份与来源说明 | 计划和设计卡；不参与语义摘要哈希 |
19: 
20: 每拍记录全部角色的动作与表演。before 继承上一拍 after，包括角色、environment、camera_side。第一拍 transition=start；之后 continuous 保持 shot_id，cut 改变 shot_id。一镜到底全程一个 shot_id，越轴需要可见过渡。状态文字相等不证明物理成立。
21: 
22: ## 修订流程
23: 
24: 改动事实或表达后，先检查状态，再编译供复核的内容：
25: 
26: ```bash
27: python scripts/combat_tool.py status my.plan.json
28: python scripts/combat_tool.py compile my.plan.json --out review-input.json
29: ```
30: 
31: review-input.json 按 headers 和各主段提供 facts、expression、input_digest、expression_digest。独立比较两者，修正遗漏或矛盾，再编译。重点是身份/动作、镜头/时间、能力/代价、连续性；不能只看标签齐全。
32: 
33: 将实际复核结论保存为 receipt JSON。每条必须复制所检查版本的两个 digest，并用具体证据填写四项 checks：
34: 
35: ```json
36: {
37:   "plan_id": "your-plan-id",
38:   "reviews": [{
39:     "scope": "P01",
40:     "input_digest": "从review-input中复制的64位哈希",
41:     "expression_digest": "从review-input中复制的64位哈希",
42:     "reviewer": "实际复核者名称",
43:     "method": "agent",
44:     "checks": {
45:       "identity_action": "说明该段兵器、动作和回应与细拍如何一致",
46:       "camera_timing": "说明该段时间与镜头规则如何对应",
47:       "ability_cost": "说明能力限制/代价的表达；无能力时说明不适用",
48:       "continuity": "说明起止状态与相邻段的关系"
49:     }
50:   }]
51: }
52: ```
53: 
54: 示意哈希不可直接执行。method 可选 human 或 agent。receipt 可只包含重新检查的 scope；其余旧记录保持，但不能绕过已失效的检查。
55: 
56: ```bash
57: python scripts/combat_tool.py apply-review my.plan.json --receipt receipt.json --out reviewed.plan.json
58: python scripts/combat_tool.py validate reviewed.plan.json
59: python scripts/combat_tool.py render reviewed.plan.json --platform generic --out-dir output/check
60: ```
61: 
62: ready 仅表示复核声明对应当前事实和表达。stale 表示内容已变化；needs_semantic_review 表示没有复核声明。后两者阻止正式导出。不要为通过导出而只刷新哈希：程序无法判断复核者是否认真读过内容。
63: 
64: 全局人物/能力/时间变更影响所有段；某段动作或摘要变化影响本段；前序结束状态和能力变化也影响后续段；最终状态变化会使总设定复核失效。哈希对 JSON 对象键顺序、数字 1/1.0、文本首尾空白和行尾差异归一化，保留正文内部语义差异。
65: 
66: ## 旧计划与文件保护
67: 
68: ```bash
69: python scripts/combat_tool.py migrate old-1.0.plan.json --out migrated.plan.json
70: ```
71: 
72: 迁移保留事实和表达，新增空的复核记录；不自动确认旧摘要正确。compile、migrate、apply-review 默认拒绝已有输出、链接路径及源文件覆盖。render 导出 7 份：design-card.md、director.md、prompt.txt、prompt-handoff.json、handoff.md、review.md、combat-plan.json。只有 render 提供显式 --force。
73: 
74: validate 和 render 接受 --max-duration 15；确认平台上限为15秒时，30秒单次计划失败，不自动拆分。内置平台模式保持未知；可使用带证据的 --profile 文件进行能力冲突检查，见[平台交接](platforms.md)。审片记录与下一段起点见[审片回流](review-loop.md)。
75: 
76: 校验器审计随包 Schema 的关键字；未知断言明确失败，不静默忽略。它是标准库实现的有限子集，并额外拒绝要求非空的纯空白字符串，不是通用 JSON Schema 引擎。结构、引用与复核版本可由代码检查，表达忠实性仍由复核者负责。
