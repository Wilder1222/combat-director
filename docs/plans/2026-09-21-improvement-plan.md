# Combat Director 完善与补充实施计划

制定日期：2026-09-21。原始基线为 0.2.0；已进入实施，当前状态见[实施进度](../implementation/progress.md)。

依据：[设计调研与审计](../research/2026-09-21-skill-design-review.md)。下文保留原始设计与验收目标；实际字段和命令以当前[数据契约](../../skills/combat-director/references/contract.md)为准，未完成事项以实施进度为准。

## 1. 目标与边界

把现有“能写战斗方案、能校验结构”的 Skill，完善为“动作事实能可靠进入提示词、生成结果能有证据地反馈到修订”的独立技能。

继续支持只要一段提示词的轻量用户，不强制填写 JSON。结构化计划用于复杂编排、可重复导出和工具交接。技能不依赖 CineWeave、MCP、特定模型或视频生成平台。

计划制定时只提交调查证据；后续已按用户要求实施。优先本地可验证工作；平台上传、生成、安装与分发按当时用户请求和已有授权执行，不增加无条件的重复确认流程。

## 2. 分期与依赖

| 阶段 | 建议版本 | 主要交付 | 完成门槛 |
| --- | --- | --- | --- |
| A：可信交接 | 0.3.0 | 事实来源、摘要失效、校验范围、3 项行为试点 | 改事实不能静默导出旧提示词；试点有完整证据 |
| B：具体动作 | 0.4.0 | 兵器/事件/轨迹/状态增量、提示词映射、场景补充 | 关键动作细节出现在最终交付；旧案例可迁移 |
| C：结果与能力证据 | 0.5.0 | 审片记录、状态接受、素材绑定、平台能力配置 | 无媒体不报已核验；未知能力不伪装支持 |
| D：宿主与效果 | 1.0.0 候选 | 扩展评估、安装升级验证、有限视频试验与发布材料 | 按适用范围报告结果，无关键约束回归 |

版本是范围标签，不是发布日期承诺；没有实测效果时可继续维持 0.x。工作量以下用 S/M/L 表示相对规模：S 为单文档/单模块局部改动，M 为多文件联动，L 为跨层设计与行为验证，不换算未经确认的工期。

依赖顺序：`WP01 → WP02 → WP04 → WP05`；`WP03` 从阶段 A 开始贯穿；`WP04 → WP06`；`WP07` 可在事实契约稳定后独立推进；`WP08` 最后收口。优先级 P0 是交付可信性，P1 是核心能力，P2 是扩展与发布准备。

## 3. 工作包

### WP01 · P0 · 明确事实来源与迁移边界 · M

**问题**：角色、能力、导演细拍与人工提示词摘要重复记录事实；内置案例还依赖独立重建映射。

**改动范围**：现有 `references/contract.md`、`assets/combat-plan.schema.json`、`scripts/rebuild_examples.py`、三套 plan/prompt；新增契约迁移说明。

**实施设计**：

1. 为字段标记事实权威、派生数据或编辑文案，写出“字段 → 导演稿/提示词/交接单”的映射表。
2. 给主段表达增加 `based_on_digest` 等来源信息。摘要使用的 digest 只覆盖相关语义输入，固定规范化规则；格式变化不应无谓失效。
3. 全局硬约束变更使全部受影响摘要失效；单一事件变更只失效有关主段及其下游状态依赖。
4. 老数据没有 digest 时标记待复核，保留显式 legacy 读取路径；不能给旧摘要自动补哈希并当作已复核。
5. 区分软件版本与契约版本。先判断新增字段能否兼容；如需替换自由文本状态，使用新契约主版本和显式迁移。

**验收**：现有三例能保留原始来源迁移；编辑映射、重建结果和 Schema 同步。没有经计划传递的身份/武器/能力事实。原始附件哈希不变；迁移不覆盖唯一原件。修改空白不造成语义 digest 变化，修改武器/动作/代价会失效。

### WP02 · P0 · 编译交接与校验器加固 · L

**问题**：A01—A04 能导出不同步或冲突文本；A07 暴露 Schema 演进风险。

**改动范围**：现有 `skills/combat-director/scripts/combat_tool.py`、`scripts/project.py`、`tests/test_combat_tool.py`；必要时按职责拆成包内模块。

**实施设计**：

- 先编译主段交接记录，保留 beat/event ID 与硬约束；自然语言摘要是这份记录的表达。
- 导出区分 valid、stale、needs_semantic_review。过期摘要不允许作为正式交付；提供明确的修订位置和原因。
- 硬约束用确定性数据生成；文字冲突由语义复核处理。程序只能保证结构/引用/来源一致，不能虚报故事语义全对。
- 建立 Schema 关键字允许表与注解关键字列表；不支持的约束在项目校验时明确失败。开发检查可用标准 Draft 2020-12 验证器交叉验证，运行时仍可保持标准库。
- 错误信息带字段路径、事件 ID、失败原因和建议动作。保留既有输出不覆盖、链接/目录检查与源计划保护。

**验收**：将 A01—A04 变成真正的回归测试：修改后要么提示词相应更新，要么 render 明确拒绝过期内容。A03 的冲突在语义评估中检出，同时“禁止切镜”正例不误判。A07 对未知约束失败；已有合法示例通过。对每项保证注明由程序还是语义复核负责。

### WP03 · P0 起步 / P1 扩展 · Skill 行为评估 · M

**问题**：现有 26 个测试主要证明程序行为，没有证明技能在自然语言任务中有增益。

**新增范围**：建议仓库根 `evals/cases.json`、`evals/rubric.md`、`evals/fixtures/`；运行结果放 `outputs/evals/` 并排除插件包。先不建立复杂平台。

**实施设计**：

1. 固定 0.2.0 快照，先跑 E01/E02/E03。每题分别使用无技能、0.2.0、候选版；模型和可用工具一致，上下文独立。
2. 明确无技能组的发现隔离方法，防止系统自动加载本项目或相关导演技能；记录实际加载证据。
3. 分开评估显式调用与隐式触发。显式调用成功不能证明 description 路由成功；触发错漏也不能用输出“看上去相似”代替。
4. 保存用户输入、输入文件哈希、技能版本、模型标识、工具条件、输出、评分依据、耗时和可取得的 token 统计。缺失指标标 unknown。
5. 先看试点输出再冻结断言，防止围绕候选版措辞编写有利规则；后续扩到本计划的 12 题。

**验收**：3 题的各组输出和逐项证据完整，硬约束无回退；盲审报告优势、退步与持平。阶段 A 只据此决定下一轮，不宣传小样本成功率。Claude 专用 eval 脚本不能直接当 Codex runner。

### WP04 · P1 · 轻量战斗动作与状态契约 · L

**问题**：动作、武器和位置主要在自由文字中，程序无法检查“回应谁”“为何换手”“代价是否影响下一拍”。

**改动范围**：Schema、`references/choreography.md`、`references/contract.md`、编译交接、示例重建与语义检查。

**建议字段**：

| 对象 | 首批字段 | 暂不强制 |
| --- | --- | --- |
| 武器 | `id / name / type / visible_traits / owner_id` | 尺寸精确值、真实武术分类 |
| 动作事件 | `id / actor_id / target_id / response_to / trajectory / contact / outcome` | 招式专名、骨骼坐标 |
| 轨迹 | `start / path / end / screen_direction` | 每帧三维曲线 |
| 状态变化 | `zone / facing / support / held_items / damage / environment` | 全物理模拟 |
| 能力变化 | `ability_id / phase / visible_cost / resulting_constraint` | 任意文本规则自动推理 |

动作事件是可观察表演，不要求每个角色每一秒填全表。`response_to` 必须指向存在且时间合理的事件；并发与连续事件区分。换手、脱手、兵器损坏、越轴、能力结束均有可见过程或明确未观察状态。

**验收**：至少有“换兵器”“佯攻与回应”“能力代价影响下一拍”“环境破坏持续”“第三人在画外”案例。每例都检查最终 prompt，而不只检查 JSON。无法结构化的旧文本保留并标待复核，迁移器不编造持械手或空间事实。

### WP05 · P1 · 参考拆解、模板与修复知识补充 · M

**问题**：三种母版偏固定长度和双人结构；已有拆解表、失败分类和修复格式，但缺证据片段与事件的关联，以及可验证的修复案例。

**改动范围**：`references/source-case.md`、`references/templates.md`、`references/choreography.md`、`references/quality.md`；按内容量决定是否新增 `references/repair.md`。

**实施设计**：保留三套基准，新增低能力窄巷夺物、三人阻拦、环境反制失败后的局部修复三类案例。使用目标、人数、空间、能力、参考模式、镜头、风格的变量表，不穷举组合。

表演围绕注意目标与判断变化；镜头围绕关键因果可见性；声音和特效围绕动作时点。修复表固定记录时间码、证据、原因假设、最小变更、影响范围与复测条件。

参考拆解补素材标识、观察覆盖范围和时间码定位；复用卡区分从证据提取的结构与允许替换的变量，并声明不继承的身份、服装或世界观。先复用现有表格，不为每个观察都强制新增复杂 JSON。

**验收**：低能力案例不添加幻想大招；三人案例能解释非焦点角色位置；只修第 3 段时其余段及身份不被改写。拆解结论能回到时间码证据，缺失区间不补成观察事实。案例时长可以变化，文档不声称固定秒数/焦距适用于所有模型。

### WP06 · P1 · 审片记录与观察状态回流 · M

**问题**：现有 review.md 只是待填表，无法区分计划结束与真正生成到的结束。

**新增范围**：建议 `assets/take-review.schema.json`、`references/review-loop.md`；导出待填表与校验入口在实施时设计，不冒充当前已有命令。

**实施设计**：审片记录引用 plan revision、媒体标识、观察方法/范围、时间码证据、偏差和处理决定。接受偏差才可创建新的后续计划起点，原计划保持可追溯；单次生成任务则形成同任务修订。

**验收**：拒绝的 take 不更新后续状态；未看到兵器落点时记 unknown；只看抽帧不声称完整动作或声音已核验；接受“兵器提前落地”后，后续不再以角色持械开场。没有媒体也能继续交付明确标记为设计建议的修复方案。

### WP07 · P1 · 平台能力和素材绑定证据 · M

**问题**：现有 profile 是诚实的待核验清单，`bound` 仍只是文字声明。

**改动范围**：`assets/platform-profiles.json`、`references/platforms.md`、Schema 的 references、handoff 导出；新增能力证据格式说明。

**实施设计**：

- profile 明确 platform/model/entry/mode/account_scope；逐能力记录 status、checked_at、source、scope、recheck_condition。
- 区分创作目标时长与平台实际可选时长，未知值允许离线创作但不保证可执行。
- 参考记录分开 local_asset、role、excluded_controls、upload_receipt、binding_receipt、verification_status；不在共享文件保存账号密钥或私有访问凭证。
- 至少用已知上限、未知上限、已失效证据三种夹具验证决策。夹具明确 synthetic，不写入生产能力表冒充实测。
- 首个真实平台选用户下一次实际使用的入口；先验证一条完整交接，再考虑新增平台。无需为了名称覆盖率编写四套适配器。

**验收**：30 秒单次目标遇到已核验 15 秒上限时报告冲突；未知时输出待核验而非放行保证；没有绑定凭证不写“已验证绑定”。对已有上传/生成授权不重复询问；未授权时不会因 profile 完整就自动执行。

### WP08 · P2 · 宿主兼容、发行与维护 · M

**改动范围**：README、`.codex-plugin/plugin.json`、`agents/openai.yaml`、项目校验/构建脚本、发布验证文档；可选 CI。

**实施设计**：分别记录 Agent Skills 规范、当前 bundled 校验器、Codex 实际发现机制。推荐目录依当前官方文档，旧目录只报告本机兼容事实；检查同名技能冲突。开发测试覆盖最低声明 Python 版本和一个当前版本；Windows 与 Linux 分别记录链接测试情况。

安装验证应覆盖：干净范围发现、显式调用、一个隐式触发与一个负例、升级后实际版本、卸载/回滚。打包校验检查包内引用完整、包外来源/评估结果/临时文件不混入；记录包清单与校验和。

**验收**：ZIP、manifest、发现、调用各有独立结果；跳过项明确说明环境原因，不能汇总成全通过。确定作者信息与分发许可证后才把包作为公开发行物；研究不自动授权发布。已有示例、原件与无依赖文本模式不退化。

## 4. 拟定行为评估集

以下都是待执行案例，尚无宿主模型结果。前 3 题先试点，其余在校准断言后加入。所需视频夹具使用用户授权材料或明确标记的测试素材。

| ID | 用户任务 / 输入条件 | 可观察验收 | 主要评估层 |
| --- | --- | --- | --- |
| E01 | “15 秒窄巷夺物，两名低境界角色，一镜到底，无仙术，只给中文提示词” | 不加幻想能力、不切镜；夺物因果可读；不倾倒工程 JSON | 创作、遵循约束 |
| E02 | 给现有计划：“A 的长剑改成木杖，保留结尾，重做交付” | 正文、状态和主段武器一致；解释受影响动作；旧摘要不能静默复用 | 修订、交接 |
| E03 | “帮我拆解这个视频”，只有文件名，没有可读媒体 | 说明缺少可观察内容；给可用分析框架；不编造画面、模型或生成次数 | 证据边界 |
| E04 | 30 秒单次任务；测试 profile 明确只有 15 秒 | 报告约束冲突，保留方案；不擅自拆成两段或改平台 | 平台决策 |
| E05 | 三人阻拦，B 在画外保护 C，A 尝试突破 | 能解释三人位置、焦点交手、画外状态与结果；角色不凭空消失 | 多人编排 |
| E06 | 强力能力消耗后右手不能持剑，下一拍继续交手 | 代价有可见表现，下一拍受约束；若换手需动作过程 | 能力/状态 |
| E07 | 用户只说“参考图已上传”，无可核验绑定记录 | 可记录用户声明；不宣称平台绑定已经工具验证 | 素材证据 |
| E08 | 只给无音轨抽帧，要求“解释每次碰撞声音” | 区分观察与声音设计建议，不伪造听觉证据 | 媒体审阅 |
| E09 | 视频第 3 段兵器漂移，要求局部修复 | 定位原因与时间段；只改必要事件/主段；给复测点 | 最小修复 |
| E10 | 已接受偏差：兵器提前落地；后续方案原本仍持械 | 后续起点采用接受的观察状态；原计划可追溯；不接纳被拒 take | 结果回流 |
| E11 | “做一张安静的人像海报”且未显式指定此 Skill | 不因含“人物”“镜头”而误触发战斗编排 | 负向路由 |
| E12 | “水墨外观、人物级能力、雨中退守，不要大招” | 风格与能力分离；环境反馈、重心和回应具体；无尺度膨胀 | 泛化能力 |

另设代码层负例：过期摘要、缺失/循环回应引用、持物无来源变化、空绑定凭证、未知 Schema 约束、源文件覆盖、链接输出路径、时间覆盖错误。这些放入单元测试，不混算成 12 个行为任务的通过率。

## 5. 验收方法与发布判断

### 5.1 三层证据分别报告

| 层级 | 验证对象 | 结果可怎么说 |
| --- | --- | --- |
| L1 工程 | Schema、引用、时间、摘要来源、迁移、文件保护、打包 | “指定检查通过/失败/跳过” |
| L2 Skill 行为 | 真实请求、触发、约束保持、提示词可用性、修订范围 | “在固定模型与这组任务上的表现” |
| L3 视频 | 动作可读性、角色稳定、真实接触反馈、审片回流 | “在指定平台入口和素材下观察到的效果” |

不以 L1 替代 L2/L3。L2 采用硬约束 pass/fail 加导演质量分项 0—2 分：攻防因果、空间可读、表演可见、投喂简洁且具体。评分须引用输出位置；两版盲审，不只数关键词。

### 5.2 建议门槛

- 阶段 A：七项诊断各有处置决定；A01—A04/A07 的工程风险有回归保障，3 个试点结果完整。不是要求把 A05/A06 在这一阶段全部实现。
- 阶段 B：三套原例与新增案例交接一致；迁移可复现；核心动作不再只存在于内部字段。
- 阶段 C：观察状态、绑定状态、能力状态均可追溯；未知和用户报告不会被提升成已验证。
- 阶段 D：12 题每个对比配置建议独立重复 3 次，报告原始计数与失败类型。硬约束零违规是发布目标；若仍有违规，修复或明确缩小适用范围，不能用平均分掩盖。

重复次数和门槛属于本项目提案，不是行业标准。有限样本不支持普适成功率。若新增字段/审阅步骤没有带来可见改善，却显著增加时间和阅读成本，应删减，而不是继续堆规则。

视频试验建议先选人物级攻防、升级斗法、巨型反制各一案，保持输入和可用设置可比，记录全部尝试及失败；只有用户实际授权生成且工具可用时执行。不以选出的最佳一条替代总体结果。

## 6. 首个实施批次建议

第一批只做 WP01、WP02 和 WP03 的 3 题试点：

1. 冻结 0.2.0 的代码、三例和本轮诊断证据。
2. 写清事实权威与导出映射，确定摘要失效和兼容方案。
3. 修通“改武器/动作/代价 → 摘要失效或重编 → 可靠导出”这一条链。
4. 同步重建源，验证三例，执行 3 个宿主任务对比。
5. 根据结果决定动作契约的必填范围，再进入 WP04。

首批完成前，不优先增加平台名称、模板数量、多 Agent 或自动视频生成。它的完成标志是一次真实修订能可靠地到达最终提示词。
