# Combat Director：战斗成片问题审阅与优化方案

日期：2026-09-30。状态：方案完成，运行技能、适配器、Schema 与安装版本尚未修改；未提交新视频生成。

## 1. 结论与审阅范围

当前主要缺口是从完整导演分析到可生成画面的转换：现有规则擅长约束身份、因果和连续性，但投喂稿仍容易输出过量细节，缺少对关键动作在指定场地和构图中能否发生、能否看见、是否产生足够明显结果的检查。战斗场景、环境状态和运镜必须参与上游设计；继续增加招式条目或负面禁令，不能直接解决本次样片的停顿和接触不清。

本次依据仓库源码、已安装入口、本对话的生成历史读取及抽帧观察。没有将一次样片失败推广为模型或技能的通用成功率，也没有将之后的兵器大场面草稿视为已生成的成功对照。

用户随后明确要求同时考虑战斗场景、环境、运镜，并调用CineWeave Director。本方案已读取其3.1.0包内的场景、动作、镜头、分镜节奏与审阅路由，采用“场地事实 → 攻防调度 → 镜头覆盖 → 提示表达”的方法。它们是创作方法与可选交接参照，不新增安装依赖，也不把CineWeave的计划能力写成生成执行能力。

## 2. 主要问题

### F01 / P0：导演层与投喂层在输出端仍混合

依据：`SKILL.md`第90—114行提出两层时间轴和八标签交付；`prompt-craft.md`第72—78行又要求压缩。`combat_tool.py`第123—138行实际依次输出硬约束、四类头部、每段全部八标签、可选具体交手和全程连续性。

只读调用 `deliverables` 的结果如下，字符数含标签与换行：

| 示例 | 时长 | 主段 | prompt.txt字符数 | LibTV/小云雀正文 |
| --- | --- | --- | --- | --- |
| grounded-15 | 15秒 | 4 | 2405 | 完全相同 |
| epic-30 | 30秒 | 6 | 4191 | 完全相同 |
| motion-blade-12 | 12秒 | 4 | 2237 | 完全相同 |

长度本身不是模型失败证明。问题是没有选择信息优先级、消除重复和保护主要事件的独立转换步骤。“用户只要提示词”目前主要省掉解释，未保证提示词本身精简。

本次对话是自由文字创作，没有调用导出器；代码问题是独立确认的系统性风险，不是本次实际执行链的断言。

### F02 / P0：文字上有因果，不等于镜头能表达因果

现有动作描述要求手、路径、接触、支撑很完整，但缺少在最终构图下的可见性审查。宽袖全身人物、较远景别与贴腕小动作的组合，使重要变化落在画面难以辨认的部位。

应将动作交付落实成“可见威胁 → 对手被迫采取的回应 → 明显改变的身体/位置/武器/环境结果”。手腕、脚尖和微表情只在影响结果且能拍清时保留。

不能把本次480P问题推广成禁止细动作；有合适近景、服装与接触构图时，细动作仍可使用。

### F03 / P0：保守默认值缺少明确的类型意图分支

`SKILL.md`第41行默认人物级、没有明确能力时不加仙术，第66行又写普通动作足够时不追加法术。原意是保护能力边界；但对“仙侠斗法”的明确请求，需要积极选择获准的幻想表现，而不是沿用普通交手的克制默认。

本次确实生成了仙术，因此不能说该规则绝对禁止仙侠。问题是缺少从用户目标到场面尺度、武器、技能机制、冲击范围的选择方法，容易由执行者把“防止乱加能力”理解成“尽量少表现能力”。

应区分：只提供仙侠服饰；明确要求仙侠战斗；明确要求大场面兵器斗法；已有正史能力上限。后两类的已授权方向不再重复询问，也不能被默认低烈度覆盖。

### F04 / P0：连续恢复有规则，连续施压缺少输出检查

`prompt-craft.md`第22行已明确不要每招重摆起手，核心入口也允许格挡回弹接反击。因此本次停顿不能只归因于缺规则；执行没有落实既有规则。

与此同时，示例和完整轨道会反复出现落稳、收回、回到胸前、再次面对。各段均以恢复完成结束时，整个片段容易被写成逐招展示。

修订应检查下一次威胁何时到来、当前恢复是否直接接下一动作、对方等待是否有原因。保留有意蓄势、威慑、受伤恢复和用户指定定格，不能用“永远不停”替代节奏设计。

### F05 / P1：仙侠大场面缺少短时长、可迁移的构成方法

现有升级式母版有30秒十一拍示例；文档也明确说不要固定套用。仍需要补足15秒等短片如何保留升级感而不搬入全部步骤。

大场面至少同时考虑：人与场景的尺度参照；能力的形状和跨越距离；攻击如何改变路线；能够看见的落点与环境后果；展示这些关系的景别。不能只写“巨型、震撼、高燃”，也不强制所有片段都巨刃对轰。

给定参考文本时，要提取“追击不中断、由近及远、终局升级”等结构，分开原文人物、武器、能力和镜头要求。30秒改15秒时重新选择主要事件，不能保留全部交换再要求更快。

### F06 / P1：LibTV交接尚未形成当前链路的核验闭环

核心 `platforms.md` 已要求区分作者文本、实际提交、平台改写和原片，方向正确。现有 `--platform` 只影响交接与能力检查，同一计划的提示词正文不变；这是通用交接，不应当作经过验证的平台提示优化。

LibTV独立入口仍为旧版手工维护，构建器主要检查格式和打包。需要当前任务范围的引用映射、编辑后文本和生成历史回读；无需为了“适配”硬编造平台偏好、字符上限或私有语法。

图片引用重复应是可审阅的诊断项，不是绝对禁止多次引用。动作参考、局部身份绑定等合理重复需保留，不能简单按字符串去重。

### F07 / P1：质量验证覆盖工程正确性，对成片表现的覆盖不足

`combat_handoff.py`现有四项复核为身份动作、镜头时长、能力代价、连续性；哈希用于绑定已审版本，不证明语义或观感。现有测试充分关注时间覆盖、身份、引用、持物和导出失效，但没有自动判断停顿、接触可读性或高潮是否成立。

`docs/validation.md`明确没有媒体结果；2026-09-29媒体试点仍是未生成草案。这些是如实披露的证据边界，不是虚假测试。不过当前发布验收还不能支持“战斗视频效果好”的结论。

不能补一组关键词测试就宣布解决：成片的攻防可读性与张力需要正常速度观看及局部连续帧证据。

### F08 / P1：版本、源码和实际使用之间存在维护断层

仓库、安装缓存、独立适配版本不同，且本次核心导出逻辑跨版本未变。需要在问题复现与发布交付时记录实际加载路径、版本和哈希，分别验证核心与适配。不能只改缓存，也不能把“构建包已生成”视作“日常调用已升级”。

### F09 / P0：场景有锚点规则，尚缺稳定的空间设计步骤

核心入口已经要求场地入口、出口、支点与路线，`combat-modes.md`也覆盖追逐、掩体和跨区。问题不是没有场景意识，而是缺少将地形、路线、兵器作用范围和相机可达空间汇合成一份可检查场地图的方法。

现有Schema有自由文本锚点、状态与可选动作zone/support；没有因此获得自动空间推演能力。本次为解决滑步增加石脊，但最终画面未清楚建立B怎样利用它。为了补一个动作而临时加地形，可能增加理解负担。

参考CineWeave场景路由：先确定场景叙事用途、空间分区、通路/障碍、尺度、材质、相机通路和光源，再设计人物调度。道路不连通、跨度不合理时先修场地或动作，不能靠推镜、切镜和新增负向词掩盖。

### F10 / P0：环境轨常停留在效果反馈，尚未充分改变攻防选择

现有粒子规则已覆盖来源、路径、介质、碰撞和结束，值得保留。但“有水花、尘土、碎石”不等于场景参与战斗。环境应有初始状态、受力变化、持续结果以及对下一次攻防的影响。

例如剑沟截断直线追击，迫使绕向仍可通行的石沿；风压推开雾层，暴露刚才被遮挡的飞剑；被击碎的掩体不在下一镜复原。此类关系不需要每场都加入，仅选真正改变结果的一项。

还需区分物理光源、法术临时照明与风格处理。固定日光方向不能随镜头任意跳变；法术亮起时，邻近衣料和石面可受光，收招后应退去。不能只追加“电影感逆光”，忽略白衣过曝、黑衣失层次、两人轮廓被雾遮住。

### F11 / P0：镜头规则强调连续性，缺少对“为何运动、要看见什么”的交付检查

现有 `action-design.md` 已要求镜头突出本拍变化，也提醒不能强加固定切镜公式。这些规则需要进入实际投喂稿和验收，而不只停在按需参考。

每镜应有观看目的、注意力顺序、构图层次、运动动机与起终位置。近景用于读清关键持械接触，宽景用于交代路线和攻击落点，超远景用于建立大招与场地尺度；这是可选功能，不是每片固定三镜。

快速推拉、环绕、升空、抖动不能代替人物动作，也不能为了“高级”同时堆入一镜。用户要求一镜到底时，设计可行的连续路径；允许剪辑时按动作因果和信息变化安排切点。单镜只保留一个主导运动意图，必要复合运动需说明各自作用与时间。

## 3. 目标工作流

用户意图和参考 → 战斗场地及环境初态 → 双方路线与攻防结果 → 按事件选择镜头覆盖 → 六轨及环境状态同步 → 可见性与节奏检查 → 精简投喂稿 → 真实提交核对 → 成片观察与定向修订。

六轨继续作为导演分析方法，不要求每个投喂主段都展示全部标签。用户要求详细六轨、逐秒稿或工程计划时，仍完整交付。

投喂稿的最小内容是：身份与武器映射、必要能力机制、主要空间关系、每段攻击及回应和结果、镜头目的、少量针对性的连续性约束。删冗余时保护武器、轨迹、交接、回握和必要落脚，不压成“激烈交锋、连续大战”。

以下只作为测试候选：15秒片段先尝试2—3个主要结果；是否切镜由用户与构图决定。500—800字可作为某次压缩对照的编辑目标，不写成技能硬上限，更不宣称是模型限制。

### 3.1 三项前置设计与一份覆盖检查

内部使用下表组织设计，普通提示词任务不要求向用户倾倒完整表或JSON。

| 设计对象 | 必须解决的实际问题 | 下游只保留什么 |
| --- | --- | --- |
| 战斗场地 | 为什么在此交战；角色起点、距离、高差；可走区域与连接；掩体、出口、危险边缘；兵器扫掠空间；相机能走哪里 | 本镜可见且影响动作的空间事实 |
| 环境状态 | 地面材质、干湿与碎屑；风向、雾层、雨雪；光源位置与方向；可破坏对象；破坏后是否改变通路 | 直接受本次攻防影响的变化及其延续 |
| 镜头方案 | 观众先看什么、再理解什么；景别、观察侧、高度、前中后景；跟谁、为什么动、何时停；焦点与切点 | 一条清楚的镜头意图和必须可见的动作阶段 |
| 事件覆盖检查 | 每次主要威胁、应对、接触/避让、身体后果和空间变化，分别由哪个镜头展示 | 不漏关键因果，不为补覆盖机械增加镜头 |

场地与环境是上游事实，镜头选择其可见部分；镜头不能移动山峰、创造落脚平台或使攻击穿过掩体。一次修复先找到拥有问题的领域，再重新生成受影响的下游内容。

### 3.2 本次仙侠兵器题的设计示意

以下是待验证的创作示意，不覆盖用户已经锁定的设定，不是新增成片事实。

场地先设定为宽阔山巅石台，中心交锋区、北侧绕行带与西侧A的退路连通；南侧断崖和远山作为尺度参照。A、B开场在中心交刃，角色真实移动后才拉开距离。石台不能一面被描述为狭窄断桥，一面允许巨幅横扫和并行奔跑。

| 段落功能 | 场地如何参与 | 环境结果 | 镜头为何这样安排 |
| --- | --- | --- | --- |
| 近身破招 | 中心区容纳交刃，A向西退让有明确通路 | 一道追斩在中心留下沟痕，局部直线路径受阻 | 斜侧近景读清刀剑接触，后撤显露A退路及攻击落点 |
| 御剑追击 | A在西侧控制剑影，B被迫沿已建立的北侧通路绕近 | 剑影落点沿B身后延伸，旧沟痕仍在 | 较高宽景同时保留施术者、追击路线与避让通道；相机保持已建立观察侧 |
| 大招碰撞 | 攻击在中心区相遇，双方退向各自仍完整的地面 | 中心石面开裂，云雾受冲击向外扩散，边缘与人物轮廓仍可辨 | 后撤升高展示人物、巨刃/剑流、石台、山体四层尺度，稳定落在能读清双方结局的位置 |

这里只选“追击路线被地面变化迫使改变”作为主要环境机制，不再叠加结冰滑倒、拾取道具和第二套地形机关。用户要一镜到底时，用连续且有时间预算的机位路径重排上述覆盖；不能把表格三个段落自动等同于三次剪辑。

### 3.3 与CineWeave的可选协作边界

| CineWeave提供的方法/已有产物 | Combat Director负责保留与编排的内容 |
| --- | --- |
| SceneSpec / SceneState / SceneLightState | 地形、材质、环境初态和光源事实；动作只能在这些条件中发生 |
| ActionSequenceSpec | 多节拍威胁、回应、轨迹、结果、空间变化及所需覆盖 |
| ShotSpec / Storyboard / SequenceRhythmSpec | 对既有动作选择构图、机位、切点和节奏，不能重新发明攻防结果 |
| CreativeReview / RepairPlan | 问题归属和最小修复变量；场地问题先改场地，镜头问题先改镜头，再同步下游 |

没有这些正式产物时采用等价的简短工作稿即可；不伪造ID、版本或哈希，不强制依赖CineWeave安装，不自动引入完整世界观或庞大合同图。

### 工程实现边界

1. 先完成WP01—WP03的文字候选及行为比较，再决定程序表示；避免一开始新增大量必填JSON字段。
2. 为工程导出新增显式的精简提示表达及其复核范围，不能用截断、删除固定字数或在导出器中偷偷重编战斗实现“压缩”。
3. 旧的完整导出保留可复现路径。新的精简样式应有明确模式/格式版本和生成权威；现有Combat Plan 1.2不静默改变含义。需要扩展时先确定兼容和迁移规则。
4. 精简表达的复核依赖覆盖主要动作、顺序、武器、镜头及先前状态。修改任一相关来源后，旧的精简复核失效。
5. 新行为规则同步到LibTV适配；建立关键规则对应表与真实行为用例，不要求两份入口逐字一致。
6. 示例仍从编辑权威生成，保留旧例和旧媒体结论，不手改派生文件制造通过。
7. 不把动作精度依赖、停顿或多引用单词设为机械硬错误；自动检查只发现结构问题，语义风险交给审阅。
8. 场景、环境和镜头建议先用轻量工作卡及可选交接记录实现；确需正式空间/覆盖结构时再引入有版本的扩展。不要直接往严格的Combat Plan 1.2塞未知字段。
9. 增加镜头表达对所用场景状态、光源和动作事件的依赖复核。上游通路被破坏后，旧镜头/摘要不能继续使用已不存在的落脚点或视线。

## 5. 回归与媒体试点

### 文字行为回归

| 用例 | 必须验证的行为 |
| --- | --- |
| 15秒、双角色图、只要提示词 | 输出可复制主稿，六轨不膨胀成对用户强制展示的全表 |
| 15秒仙侠、大场面、有武器 | 明确双方武器及能力差异、尺度参照和可见交锋结果 |
| 15秒普通武侠、禁止仙术 | 不套用剑阵、巨刃或场地爆炸 |
| 12秒演武、允许停顿 | 不用追杀与无休止移动覆盖演武节奏 |
| 宽袖人物加贴腕动作 | 发现遮挡依赖，选择适合的景别或等义的大动作，不换装偷解决 |
| 一镜到底且只许近远景 | 指出连续移动必经中间景别，解释采用的理解，不暗加硬切 |
| 一份文件含两套30秒稿，改15秒 | 选择并声明来源结构、身份映射及删减，不叠加两套能力 |
| 实体飞剑离手后改近战 | 精简后仍保留回程、握回的手和时机 |
| 只读失败视频诊断 | 分开实际观察、文本推断、缺失证据；不自动消费积分修复 |
| 平台引用被增加或改写不可见 | 记录真实状态，不猜内部最终输入或把重复引用直接判作根因 |
| 同样角色与武器，从开阔石台换到窄回廊 | 路线、挥扫空间、射线遮挡和镜头通路随之改变，不只替换场景词 |
| 先前攻击破坏通路或掩体 | 下一拍继承破坏，选择可行替代路线，不靠切镜恢复场地 |
| 雾、尘与强法术光的大场面 | 有物理来源和状态变化，关键轮廓/落点仍能读清；退光后恢复原光源关系 |
| 巨刃与剑雨的尺度展示 | 人物、兵器、场地、远山可相互比较，攻击有起点和落点，远景不丢施术者 |
| 严格一镜到底的大范围追逐 | 人物和相机各有连续可行路线，推镜不代替近身，不能秘密切镜 |
| 多镜头高速交锋 | 每镜有信息增量与覆盖作用；切点继承动作阶段、视线、方向和环境状态 |

工程回归重点：完整/精简导出模式、摘要失效、主要事件顺序、实体与投影、素材映射、来源/派生同步、旧包兼容。不要用标签出现次数作为创作质量评分。

### 媒体试点设计

本轮仅设计，不调用生成。未来执行须已有明确的生成范围和预算授权。

第一组用于验证“表达压缩”：同一掌法任务、相同参考、动作事件、机位要求和设置，对比原完整稿与语义等价精简稿，每组3次，共6条。已有单条失败样片作案例证据，不冒充新版本配对重复。若为改善编排而改变主要事件，另立条件，不能仍归因于压缩。

第二组用于验证当前用户的新目标：同一兵器大场面任务，对比目前兵器草稿与新的可见性/节奏候选，每组3次，共6条。此组可以比较整套编排方法，不能把差异归因于单个词；优先在第一组或文字评估发现问题后再决定是否执行。

每条保存技能版本/路径/哈希、设计稿、实际提交文本、参考映射、模型和入口、可见设置、提示增强状态、历史回读文本、原片哈希和时长/FPS/分辨率。seed仅在真实支持时记录；无可控seed则保留随机性限制。

观看分正常速度和局部连续帧；有条件时由未参与该稿编写的评审按匿名样片编号评价。各项采用“满足/部分/未满足/无法判断”，不先用总分掩盖关键失败：

- 主要威胁、回应、接触或避让、结果是否可辨。
- 无理由停顿发生在哪里；有意蓄势与恢复是否服务下一次交锋。
- 身份、武器、持械与效果归属是否连续。
- 大场面的尺度、路线、落点与高潮是否符合本任务。
- 场景分区、通路、高差和掩体是否一致；环境变化是否真的影响后续选择。
- 镜头是否按目的展示关键事件；是否因错误跟随、遮挡或越轴导致因果丢失。
- 物理光源与法术照明是否有来源及连续变化，风雾尘屑是否掩盖必要信息。
- 速度、镜头、时长和用户指定风格是否保持。
- 音轨只在实际听取后评价。

三次重复是探索样本，不足以发布通用成功率。若模型仍不能表达某种接触，允许在同一创作目的下重新设计动作；不要反复追加“不许失败”式禁令。先通过动作验收，再决定是否生成高分辨率版本。

## 6. 执行顺序与完成门槛

建议顺序：冻结本次失败证据和版本 → WP01—WP03候选（场地/环境先于具体攻防，动作先于镜头选择）→ 十六类文字回归 → 工程与导出兼容检查 → WP04—WP05 → 获得执行条件后的媒体试点 → 根据证据收敛 → 正式构建与实际安装核验。

完成分层报告：

1. 规则完成：对应文件、案例和行为任务已更新，且没有损失普通武侠、演武和严格镜头模式。
2. 工程完成：所改编译、失效及发布检查通过，派生文件同步。
3. 平台交接完成：真实入口与实际提交经过核对，引用没有未解释的变化。
4. 媒体效果完成：有符合当前任务的原片观察和重复结果；没有媒体证据时明确停在前几层。
5. 使用交付完成：日常调用实际读取新包，版本与路径匹配；不能只交付仓库新版本。

制定方案时只完成审阅、版本差异检查及无写入导出探针。2026-09-30随后已执行WP01—WP06的软件、文档和日常安装部分，见[0.10.0交付记录](../implementation/combat-0.10.0-delivery.md)：43项发布检查、105单测、16题文字试写与2题重测、195文件安装核对及新进程发现。LibTV站内导入、实际提交与媒体试点仍未执行；此处记录优化验收状态，后续Git发布以仓库历史为准。文字测试暴露的距离问题和复测限制保留在证据中，不以实现完成代表视频效果完成。
