# Motion blur 融入计划

日期：2026-09-23。制定基线：0.8.2工作区；随后按持续的项目完善目标执行。0.8.3文字接入、案例、双层传递和独立文字评估已完成，36项发布检查通过，本地ZIP已构建；媒体试验未运行。研究阶段和实施阶段的证据分别保留，见[当前验证](../validation.md)及[行为报告](../implementation/motion-blur-behavior-0.8.3.md)。

依据：[调研报告](../research/2026-09-23-motion-blur-research.md)、[系统提示词草案及六个场景](../research/2026-09-23-motion-blur-system-prompt-draft.md)、[来源记录](../research/evidence/motion-blur-sources-2026-09-23.json)。

## 1. 预期结果与范围

技能能根据镜头意图正确描述 motion blur，区分曝光、相机运动、粒子尾迹、景深和风格化残影；压缩提示词时保留这些关系；诊断时区分创作意图、模型输出和后期处理。

第一阶段保持六轨、八标签和 plan 1.2。复用现有 camera、vfx、environment 文字字段；不新增全片必填模糊参数，不替全部旧案例加快门，不改武学能力，不向生成库手工追加卡片。

只有真实工具接入需要可执行曝光设置，并取得当前工具文档和入口证据后，才另提版本化控制契约。自然语言里写一个快门数值，不满足这一升级条件。

## 4. 双层编排与数据依赖

当前 `combat_tool.py` 直接使用 `sections[].summary` 生成八标签；它不从 `beats[].camera.path` 自动总结运动观感。`combat_handoff.py` 把该段完整 beats 纳入审阅事实，把摘要作为独立表达签名。

```mermaid
flowchart LR
    A[用户意图与已观察素材] --> B[逐拍 camera.path 和 vfx]
    B --> C[作者压缩成 section.summary]
    B --> D[handoff 事实摘要签名]
    C --> E[handoff 表达签名]
    D --> F[语义复核]
    E --> F
    F --> G[导出八标签提示词]
    G --> H[实际工具设置和视频观察]
```

首版处理规则：

1. 每个受该策略影响的 beat 都给出足够镜头说明；整片共有约束可以在 headers 中汇总，但不能只写一次后假定它已进入全部 section 的审阅事实。
2. `headers.scene` 当前不是每段 global facts 的一部分。既有 `rules` 仅允许幻想开关与尺度，不可偷偷塞新键。首版在适用 beats 与摘要里同步，暂不改变契约。
3. `inherited_states` 继承前段状态、动作事件等，不继承所有 camera/vfx 文字。跨段一致策略必须明确继续，不能只依赖第一段。
4. 改 beat 镜头说明应使包含它的 scope 输入签名改变；改分段摘要应使该段表达签名改变。这个机制证明“需要重审”，不证明自然语言物理正确。
5. 若未来出现大量“只改全局镜头规则却必须重写所有段”的真实需求，再评估独立成像契约：定义权威、版本迁移、继承作用域和失效规则。不能先加重复真值来源再补同步。

必要工程回归应覆盖：camera.path 的修改、summary.camera 的修改、缺少有效复核时正式导出被拦截、重新实际复核后正确输出；原固定机位、单镜连续、无幻想方案继续成立。优先扩展已有测试的数据变体，不为每句参考文字加字符串断言。

## 5. 12 题行为验收设计

以下保留验收设计；实际请求已固定在evals/motion-blur-0.8.3/cases.json。T06/T09措辞为未用于修订规则的留出变体；均处于已设计领域内，不声称全新领域泛化。执行者仅获取任务、必要素材和冻结技能，不获取本表或预期答案。

| 编号 | 输入情境 | 应观察的行为 | 关键失败 |
| --- | --- | --- | --- |
| T01 | 普通静态对峙，无模糊要求 | 直接编排姿态与空间；不插强拖影套餐 | 把所有场景强行电影模糊化 |
| T02 | 固定机位木杖高速下劈 | 局部轨迹与格挡恢复可辨，背景稳定 | 凭主体动作让静止背景全幅横拖 |
| T03 | 主体跟拍，另一人加速追近 | 区分主跟随、摆臂与对手相对运动 | 两人全身所有部位像素锁定 |
| T04 | 双人快速交刃，一镜到底、正常速度 | 用构图和机位安排读懂接触 | 偷加切镜、慢放、停顿或定格 |
| T05 | 用户要求干脆低模糊 | 保留观感与原动作速度 | 自动覆盖成默认 180°/强模糊 |
| T06 | 用户要求强拖影艺术段 | 标明对象、时段与信息取舍 | 为追求写实擅自删除用户风格 |
| T07 | 同一区域每帧全锐利且强长曝光 | 指明真正互斥处并给可选修订 | 假装两个要求已同时满足 |
| T08 | 二维 smear，无分身能力 | 保留画法，只有原实体参与攻防 | 变成能独立攻击的分身，或全删残影 |
| T09 | 附刃光带，挥空后止势 | 分别处理曝光、停止发射和旧粒子 | 剑停后曝光拖糊在空中自行漂散；挥空爆炸 |
| T10 | 图生视频输入有模糊线索，要求相反运动 | 有图则观察冲突，无图则声明未知 | 声称看过未读图或已修复输入 |
| T11 | 未知平台要求“90°快门已生效” | 区分意图与设置，保持能力未知 | 发明字段或宣称真实参数执行 |
| T12 | 修改 beat 镜头后使用旧摘要/凭证 | 识别表达不同步并重审；不静默导出 | 只加关键词便放行旧表达 |

另做格式变体：短提示词请求应得到短提示词；结构化任务才输出契约。正向优先与负向入口分别按已核验平台运行，不能仅凭平台名称猜测接口。

评价者把结果记为“满足 / 部分 / 未满足 / 无法判断”，附具体文本依据。能力越界、暗改速度/时长/剪辑、伪称实测或工具控制等违约不能被审美分平均抵消。自评、独立任务输出和独立复核分别标记；任何同一模型的小样本比较都不代表普适成功率。

## 6. 媒体对照试验（尚未提交任务）

### 6.1 先回答两个问题

- 明确的相对运动与可辨事件描述，是否比孤立的风格词更稳定？
- 在这些关系已经写清后，再加快门术语是否有增益，或反而引入过度模糊/顿挫？

选择三种场景：固定机位实体兵器、跟拍双人追逐、附刃粒子加交手。每个场景比较：

| 组别 | 提示词差异 | 可解释的比较 |
| --- | --- | --- |
| A | 相同动作/场地/能力，成像只写泛化电影运动模糊 | 基线 |
| B | 保持核心任务，明确相对运动、模糊范围、可辨事件与收束 | A/B 比较具体描述整包的效果，包含信息量变化 |
| C | B 基础上只加入与目标一致的一个快门观感术语 | B/C 比较该术语的附加贡献，不伪称实拍参数 |

首轮建议每场景、每组各三次，共 `3 × 3 × 3 = 27` 条作为小型探索；这是拟定试验规模，不是已消耗额度，也不足以给稳定成功率。用户明确要求无模糊/风格化残影的任务应另设相应对照，不能用本组“自然电影观感”覆盖它们。

A/B 的文字长度与信息量不同，不能把改善归因于某一个词。若初试显示差异，再设计近似等长的描述对照及更多重复。不同平台、模型版本的结果分别报告；不能混池得出“通用最优快门词”。

### 6.2 控制条件和证据

固定人物、兵器、动作因果、参考文件哈希、画幅和当前入口实际支持的时长/分辨率；记录模型版本、日期、入口、负向输入、提示增强开关、所有可见设置。支持 seed 时使用预先选定的配对 seed，并保留多次重复；不承诺 seed 必然产生可复现结果。

以平台原始下载视频为主要评价对象。插帧、补模糊、超分和变速产物另存，不覆盖原片；若平台有无法关闭的处理，记录它。不能为了匹配教学例时长拼接后仍称“原始单次生成”。总时长或模式不支持时另拟实验任务并标明差异。

每条至少保存：测试 ID、完整提示词、模型/入口/版本、参考哈希、可控参数及未知项、请求与结果标识、输出文件哈希、原始媒体时长/FPS/分辨率、处理链、失败或拒绝记录、评价者与时间码观察。媒体元数据只说明文件属性，不证明真实快门设置。

### 6.3 观察轴

匿名随机排列 A/B/C 原片，先正常速度观看，再按接触、遮挡和止势附近取连续帧核对；不只截一张最好看的图。观察：

| 维度 | 证据问题 |
| --- | --- |
| 相对运动 | 相机、主体与背景关系是否符合描述；模糊方向是否随运动合理变化 |
| 攻防可辨 | 起动、回应、接触/避让与恢复能否连续追踪，哪段看不清 |
| 实体与持物 | 手、剑、人物数量是否稳定；模糊是否被误生成新实体 |
| 成像与效果边界 | 曝光模糊、存量粒子和艺术残影是否分别结束；是否存在非预期粘连 |
| 用户风格 | 干脆/自然/重拖影是否符合本题，而非一律越清楚越好 |
| 时间与镜头 | 总长、正常/慢放区间、镜头模式是否遵守 |

各轴用“满足 / 部分 / 未满足 / 看不清”加时间码与理由，不先合成一个总分。视频本身看不清关键事件时不能算通过；只有抽帧而未看完整视频时，记录观察覆盖不足。动作和能力硬性失败单列，审美偏好另记。

若试点未见优势或出现回归，保留结果，缩短/修订规则并用新的留出题检验；不能挑最佳样本宣称成功，也不靠给评价者看目标答案提高分数。

## 7. 实施后的工程与发布门槛

MB02–04 完成后：运行修改涉及的定向测试；更新必要来源与生成产物；执行仓库要求的 `python scripts/validate_release.py`，检查发布结构、所有资源链接、示例、标准 Schema、单测、确定性构建和解压工作流。版本与 CHANGELOG 仅在实现进入发布时同步。

保留原验证失败、跳过与新结果，不把已有 0.8.2 的 33 项发布检查或 83 项单测沿用成新实现成绩。工程通过只能证明结构与流程；文字行为和视频效果各需独立证据。

若仅新增参考却导致无关场景输出膨胀，优先缩短路由、按需加载和压缩例子；若平台控制仍未知，继续交付诚实的文字意图，不虚构参数来“补全”计划。
