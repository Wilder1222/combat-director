# Combat Director：相关 Skill 设计调研与现状审计

日期：2026-09-21。基线：Combat Director 0.2.0 / Combat Plan 1.0。

本轮交付是研究与补充方案。没有修改生产 Skill、数据契约或导出器，没有安装插件、执行视频生成或发布。实施顺序见 [完善计划](../plans/2026-09-21-improvement-plan.md)。

## 1. 结论

项目已经形成了值得保留的创作骨架：目标驱动的攻防、六轨导演稿、导演细拍与投喂主段、能力边界、三类母版、来源与推断分离，以及无平台依赖的文本交付。

下一步的首要问题是**导演计划与实际投喂文本之间缺少可靠的同步机制**。代码实验确认，修改角色武器、导演动作或能力代价，校验仍通过，而提示词完全不变。增加模板、长篇知识或平台名称，都不能解决这个断层。

推荐依次建设四层能力：

1. **可信交接**：明确唯一事实来源，旧摘要失效，关键约束进入提示词，Schema 校验范围可审计。
2. **具体动作**：将兵器、轨迹、交手关系、持物和空间变化变成可选的轻量结构，并确实传到投喂层。
3. **结果回流**：实际生成结果与计划分开记录，接受的偏差才能影响后续状态；素材绑定和平台能力附证据。
4. **效果验证**：补真实用户任务评估、宿主安装验证，最后再用视频验证适用范围。

维持一个公开 Skill 入口，通过参考文档按需展开；Python 保持可选，平台执行器保持独立。六轨是画面信息组织方式，不需要变成六个 Agent。

## 3. 官方设计原则及本项目取舍

### 3.1 Skill 是任务入口，不是知识仓库的全文索引

Agent Skills 规范使用 `name`、`description` 做发现入口，支持按需加载参考材料；OpenAI 文档强调把触发场景放在描述前部。当前项目约百行入口、任务路由与相对路径已经接近合理形态，应补齐路由条件和交付约束，而不是把所有研究材料塞进 SKILL.md。[Agent Skills 规范](https://agentskills.io/specification)、[OpenAI Skill 文档](https://learn.chatgpt.com/docs/build-skills)。

建议入口只保留：适用任务、最小输入、事实与推断边界、核心工作流、按需文档表、交付检查。动作细节、审片状态、平台证据和工程契约留在各自参考文档。研究报告和开发评估留在仓库，不进入默认插件载荷。

### 3.2 规范兼容与宿主兼容分别验证

公开 Agent Skills 规范允许 `compatibility` 等可选字段；本机 bundled `quick_validate.py` 的允许字段集合不一定与规范同步。当前将兼容说明放在正文是可行折中，不应反推“规范不允许 compatibility”。

OpenAI 当前文档列出 `.agents/skills` 的项目/用户发现路径；本项目 README 用的是本机 `~/.codex/skills` 示例。下一版应记录宿主版本与实际发现结果，区分推荐安装路径、本机已有路径、插件缓存路径，避免多份同名技能互相干扰。[规范](https://agentskills.io/specification)、[宿主发现机制](https://learn.chatgpt.com/docs/build-skills)。

本机 `plugin-creator` 指南提供 manifest 校验和 marketplace 工作流，本轮只把它作为打包设计依据。ZIP 正确、manifest 正确、宿主能够发现、宿主能够调用，是四个不同的验收项。[本地指南快照信息](evidence/host-guidance.json)。

### 3.3 测试“有没有帮助”，而不只是“有没有标签”

Agent Skills 评估指南建议从少量真实任务开始，在干净上下文中比较启用技能和基线，保留输出证据及成本。对本项目，应把结构断言和导演质量分别评分：八个标签齐全不代表攻防有因果，JSON 合法不代表动作可读。先跑 3 个试点，再扩展评估集。[官方评估指南](https://agentskills.io/skill-creation/evaluating-skills)。

## 6. 推荐目标设计

### 6.1 单一事实来源与有版本的摘要

事实权威应是约束、人物、兵器、能力、动作事件和计划状态。导演文案可以自由表达，但不能另立一套人物或动作事实。投喂主段仍保留编辑价值，不要求用字符串拼接取代导演写作。

建议分三层：

- **事实层**：结构化计划，以及无结构字段时明确标记的人工描述。
- **交接层**：编译出本主段的事件、硬约束和状态变化，记录来源 ID。
- **表达层**：导演写成自然语言摘要，保存所依据的语义摘要哈希和复核记录。

哈希只证明“摘要依据的输入没有变”，不能证明文字真实正确。字段变化时应使摘要过期并阻止正式 render，或先重新编译/改写后再复核；不能仅重写哈希就宣称语义校验通过。

关键硬约束尽量由程序生成：时长、一镜到底、角色身份与兵器、能力上限、开场/终点状态。自由摘要通过独立一致性复核发现冲突。对“切”字的搜索只能预警，不能把“不得切镜”判成切镜，也不能漏掉隐含跳切。

特殊注意：当前内置案例的真正编辑源是 `scripts/rebuild_examples.py` 中的映射与归档提示词。设计新格式时必须同时更新重建路径、迁移逻辑与生成结果；只修 plan.json，下次重建仍会退回旧设计。

### 6.2 最小动作契约：为可见交手服务

建议新增三组可选结构，先用于需要细节的案例，再决定是否成为严格模式要求：

| 结构 | 最小信息 | 解决的问题 |
| --- | --- | --- |
| `weapon_profiles` | ID、名称/类型、可见形制、角色归属；持械手属于状态 | 不同兵器不再全部写成“挥武器” |
| `action_events` | ID、行动者、目标、回应的事件、动作路径、接触/避让、结果 | 明确谁针对谁做了什么，以及为何引出下一步 |
| `state_delta` | 区域、朝向、支撑、持物、损伤、环境变化；能力激活/消耗/结束 | 检查状态变化有来源，而不只检查两段文字相等 |

轨迹优先使用空间锚点、起点—路径—终点和画面方向，不要求精确三维坐标。招式名称可选；没有动作机制时，命名不能增加分数。所有细节用于虚构画面编排和可见因果，不把系统做成武术物理模拟器。

一次对打可表为“发起 → 对方回应 → 接触或落空 → 双方新位置”。多人场面只补焦点行动者、回应者、支援/画外状态，不把每个人在每一拍都写成同等详细的主角。

### 6.3 六轨保留，表演和特效以动作因果为锚点

表演用可见行为表示判断改变：视线目标、呼吸、肩颈与手指张力、重心、动作迟疑及恢复。情绪词可以保留，但应由行为承载。摄影机必须解释它让观众看见哪个动作关系，不能用推拉摇移代替人物移动。

特效需连接能力事件，明确出现、作用、反馈、结束。环境破坏进入后续状态，不能下一拍恢复原样。声音标记接触或动作时点；未听到视频音轨时，只能交付声音设计建议。

### 6.4 计划与实拍结果分开

未来审片记录至少包含 `take_id`、源计划版本、媒体标识、观察范围、问题时间码、已完成/未完成/额外事件、观察到的结束状态、处理决定。

处理决定建议采用 `accept / accept_with_deviation / repair / reject`。接受偏差必须写清其影响；拒绝的 take 不成为下一段起点；无法观察的状态保留 unknown。用户只给截图或口述时，来源分别记作抽帧观察或用户报告，不能提升为全片已核验。

连续片段只是可选扩展。对明确要求单次生成或一镜到底的用户，审片回流用于修订同一任务，不自动变成多段拼接。

### 6.5 平台能力与参考素材：证据先于适配

能力键建议由“平台 + 模型版本 + 入口/API + 生成模式 + 账号范围”组成；每项能力记录 supported、unsupported 或 unknown，以及检查时间、证据来源、适用范围和失效条件。模型支持某能力，不代表当前平台入口已开放。

先支持读取已核验配置、检查冲突、生成具体交接单；不为四个平台虚构四套措辞。不能满足 30 秒单次任务时，给出冲突和可选改法，保留用户决策，不静默换模型、拆片或上传。

参考素材分别记录：本地素材身份、用途与排除内容、平台上传/绑定记录、实际核验状态。文件存在或 SHA-256 只能证明本地素材身份，不能证明已绑定远端生成任务。

平台指南发现入口：[Seedance 2.0](https://docs.volcengine.com/docs/ark/seedance-2-0-prompt-guide?lang=en)、[Seedance 2.5](https://docs.volcengine.com/docs/ark/seedance-2-5-prompt-guide?lang=zh)、[Liblib 官方首页](https://www.liblib.tv/)。这些链接本轮不用于填写具体能力上限。

### 6.6 模板从固定故事升级为可控变量

三套现有案例保留为基线，新增案例由正交变量选取：目标（夺物/阻拦/脱身）、人数、能力尺度、空间限制、参考模式、镜头连续性、呈现风格。先覆盖现有失败面，再增加故事数量。

15/30 秒、4—6 个主段是当前案例与经验建议，不能成为平台通用限制。允许“低境界、窄巷、夺物、无特效、单镜”这类组合独立成立。写实外观与幻想能力继续分离。

### 6.7 修复要能证明改了哪里

现有 quality.md 已有失败分类、证据列和修复报告顺序，应在这个基础上补带输入与结果的案例，并关联事件/主段 ID。分类覆盖攻防无回应、武器/手别漂移、空间不连续、能力代价失效、表演不可读、镜头遮蔽因果、特效覆盖动作、节奏超载、素材绑定错误、平台约束冲突。

每次修复记录证据 → 原因假设 → 最小变更 → 影响的事件/主段 → 复测条件。优先删减冲突和过载，再调整动作、镜头与参考；只有用户允许时才改变时长或任务分段。固定“第几次重试必须换平台”缺少普遍依据。

### 6.8 从视频拆解到可复用模板，补齐证据链

现有 source-case.md 已区分可见事实、创作解读、生成方法假设和缺口，应保留。可补素材标识、观察覆盖范围、时间码/帧定位、遮挡与置信说明，并将抽取出的动作结构链接回证据片段。

拆解输出分为两部分：观察记录描述该片实际出现了什么；复用卡提取目标、攻守转折、运动路径、镜头如何呈现接触、特效与环境如何响应，同时列出允许替换的角色、场景和风格。参考人物的脸和具体身份不能变成所有新案例的默认身份。

没有完整视频时，仍可基于已有片段产出部分分析，但不能把相邻抽帧之间的位移补写成已观察的动作。成片可见切镜也不证明分几次生成；单个文件不证明无后期。工具依赖按用户材料与宿主能力选取，核心 Skill 不强制安装媒体处理工具链。

## 7. 不建议现在做的事

- 不把六轨或六部门变成强制多 Agent；增加协调成本前先证明单入口有瓶颈。
- 不复制完整工作室、资产数据库、HTML 审片站或自动生成后端。可先用本地 JSON 和 Markdown 验证需求。
- 不把第三方 Skill 的固定时长、字数、镜头参数和确认流程当作官方限制。
- 不用词表扫描替代动作质量判断，不将通过单元测试宣传成视频效果已验证。
- 不在 Skill 包里复制研究快照、原始附件、生成媒体或评估结果；运行产物放用户工作区。
- 不为“兼容 CineWeave”引入依赖；先写字段映射，并显式说明丢失信息。

## 8. 进入实施前已经确定与仍待验证的事项

**可以立即执行的工程方向**：摘要失效机制、Schema 关键字审计、重建源同步、轻量动作交接、试点评估设计。它们有本地证据支持。

**需要实验决定的设计**：动作字段的必填程度、主段压缩方式、复杂案例是否需要第二次审阅、适配器是否真的需要改变提示词正文。先观察输出，再提高复杂度。

**仍需外部证据**：平台账号能力、真实生成质量、原视频的生成流程、Codex 安装与调用表现。下一步不得将这些项目提前标为完成。
